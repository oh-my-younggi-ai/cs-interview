# 한 줄 정의

**TCP와 UDP의 선택**은 프로토콜 이름보다 데이터 유실과 순서 변경을 허용할 수 있는지, 오래된 데이터보다 최신 데이터가 중요한지를 기준으로 결정한다.

# 핵심 개념

## 보장과 데이터 단위

| 항목 | [TCP](/network/tcp.md) | [UDP](/network/udp.md) |
|---|---|---|
| 연결 | 연결 설정과 상태 유지 | 연결 설정과 상태 유지 없음 |
| 전달과 순서 | 신뢰성, 순서 있는 바이트 스트림 | 전달, 순서, 중복 제거 보장 없음 |
| 데이터 경계 | 애플리케이션이 framing | 데이터그램 경계 보존 |
| 유실 처리 | ACK와 재전송으로 복구 | 애플리케이션이 필요할 때 처리 |

## 선택 기준

- 파일 전송, 결제, 문서 변경처럼 누락이나 순서 변경을 허용할 수 없으면 TCP를 선택한다.
- 실시간 위치, 음성, 게임 상태처럼 늦게 복구한 과거 데이터의 가치가 낮고 일부 유실을 허용할 수 있으면 UDP를 고려한다.
- UDP를 선택해도 인증, 재시도, 혼잡 제어, 신뢰성 요구가 사라지는 것은 아니다. 필요한 보장은 애플리케이션 또는 상위 프로토콜이 맡아야 한다.

# 면접 단골 질문

- Q: 실시간 멀티플레이어 게임의 위치 갱신에 UDP가 적합한 이유는 무엇인가요?
  - 포인트: 최신 상태의 가치, 일부 유실 허용, TCP 재전송과 순서 보장에 따른 지연 회피.
- Q: TCP와 UDP 중 어느 것이 더 빠른가요?
  - 포인트: 절대 비교가 아니라 신뢰성, 순서 보장, 재전송의 비용과 애플리케이션 요구를 기준으로 판단.
- Q: UDP 위에서 신뢰성 있는 프로토콜을 만들 수 있나요?
  - 포인트: 가능하며 필요한 ACK, 재전송, 순서 제어를 상위 프로토콜이 구현. 요구되지 않는 기능까지 추가하지 않음.

# 헷갈리는 점 / 함정

- **"실시간 통신은 항상 UDP를 사용한다"** - 유실 허용도와 복구 방식에 따라 TCP 또는 UDP 위 상위 프로토콜을 선택할 수 있다.
- **"TCP를 쓰면 애플리케이션이 메시지 단위를 신경 쓰지 않아도 된다"** - TCP는 바이트 스트림이므로 framing은 별도로 필요하다.
- **"UDP는 보안이나 신뢰성을 제공할 수 없다"** - UDP 자체에는 없지만 상위 프로토콜이나 애플리케이션이 필요한 기능을 제공할 수 있다.
